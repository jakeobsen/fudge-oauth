# CLAUDE.md

Guidance for AI coding agents working in this repository. User-facing docs are in README.md.

## What this is

fudge-oauth is the OAuth sign-in relay for Fudge (`jakeobsen/fudge`), a macOS launcher that runs Raycast extensions. Extensions sign in through `@raycast/utils`' `OAuthService`, which talks to Raycast's proxies (`https://<provider>.oauth.raycast.com/{authorize,token,refresh-token}`) for GitHub, Linear, Slack and Asana, and to the provider for Google, Atlassian (Jira and Confluence) and Zoom. Fudge sends all seven to `<relay>/<provider>/{authorize,token,refresh-token}` instead. Store extensions also sign in through Raycast's other proxies, a host per service or the shared `oauth.raycast.com/v1/…` proxy with the extension author's own app, and Fudge sends the ones in its table to the relay's providers, where the relay's own app takes their place. The relay holds the OAuth apps' client secrets; Fudge holds none.

## Layout

- `cmd/fudge-oauth`: `main`. Loads the config, serves with timeouts and a graceful shutdown on SIGTERM (plain HTTP, or HTTPS only with TLS 1.2 at least when a certificate is configured), and has a `healthcheck [URL]` subcommand for the container's health check (the image has no shell or curl). `healthcheck` fails when the system's CA certificates don't load (`checkRoots`), then asks URL, or the relay's own `/healthz` from its config (`healthURL`: 127.0.0.1 for an unspecified listen address, `https` with TLS, skipping verification for that call only, since the certificate names the public host).
- `internal/provider`: the built-in table, one `Provider` per provider: path name, title, endpoints, whether the relay uses PKCE with it, whether it issues refresh tokens, how client credentials go (`ClientAuthBody` or `ClientAuthBasic`), the token body encoding (`BodyForm` or `BodyJSON`), and authorize parameters the relay adds when the extension didn't send them (`AuthorizeDefaults`: Atlassian's `audience=api.atlassian.com` and `prompt=consent`, which Raycast's Jira proxy added, and Zoho's `prompt=consent`, which Zoho needs to give a refresh token at every sign-in, not only a user's first). `Aliases` maps a deprecated path name to its provider (`jira` → `atlassian`, the name until v0.3.0), for one release.
- `internal/config`: `Load(getenv, readFile)`. YAML from `FUDGE_OAUTH_CONFIG` (strict: unknown fields are errors), then `FUDGE_OAUTH_*` variables override value by value, then validation. Secrets may come from files (`key_file`, `client_secret_file`), trimmed. A provider is configured once it has a client ID and secret. A deprecated name configures its provider (`providers.jira`, `FUDGE_OAUTH_JIRA_*`) where the new one isn't set, and the new one wins where both are; either way `Config.Notes` says so, by setting names only, and `logStart` logs each note once. `tls.cert_file` and `tls.key_file` go together; with them `listen` defaults to `:8443`, else `:8080`.
- `internal/tlscert`: the relay's own certificate. `New` refuses a pair that can't be read or doesn't match; `GetCertificate` re-reads the files when their modification times change, checking at most once a minute (`CheckInterval`), and keeps the old pair, logging why, when a new one doesn't load. Errors name the setting (`tls.cert_file`), never the path.
- `internal/testcert`: self-signed certificates for tests.
- `internal/seal`: AES-256-GCM sealing. The expiry is inside the ciphertext, and the purpose is the additional data. The relay's purposes are `state/<provider>` and `code/<provider>` (`purpose` in `relay.go`), so a sealed state never opens as a code, nor either at another provider's endpoints. Output is unpadded base64url.
- `internal/relay`: the HTTP handlers (`relay.go`), the token exchange with the provider (`exchange.go`), and the pages and request logging (`pages.go`). The front page (`GET /`, `index`) is registered only while `info_page` is on (`Config.HideInfoPage` false, the zero value), so with it off `/` answers exactly as any unknown path does.

## The flow

- **Aliases.** The handlers look the path up through `provider.Canonical`, so `/jira/…` is Atlassian. The upstream `redirect_uri` is always the provider's own callback (`/atlassian/callback`), since the provider compares it exactly with the registered one. A state or code a relay from before the rename sealed for `jira` still opens at Atlassian's paths (`openSealed` tries the aliases' purposes), and its exchange sends the old callback it was given (`codePayload.Callback`, or the alias's callback for an old code).
- **authorize** checks `redirect_uri` is `http://127.0.0.1:<port>/…` or `http://[::1]:<port>/…` (`LoopbackRedirect`), and requires an S256 `code_challenge` and a `state`. It seals Fudge's redirect, state and challenge, plus the relay's own PKCE verifier when the provider uses PKCE, into the provider's `state` (10 minutes). It redirects with the relay's `client_id` and callback; every other incoming parameter goes on unchanged (Linear's `actor`, Slack's `user_scope`, Google's `access_type`, Atlassian's `audience`), and the provider's `AuthorizeDefaults` are added where missing, never twice. An empty `scope` is left out, since `OAuthService.slack` sends one.
- **callback** opens the sealed state, then redirects to Fudge's redirect with Fudge's `state` and a sealed code (provider, provider's code, Fudge's redirect and challenge, the relay's verifier; 5 minutes), or with the provider's `error`. A state that won't open gets an HTML page, never a redirect.
- **token** accepts JSON or form bodies, exactly as `OAuthService.fetchTokens` sends them. It opens the code, checks the provider, the `redirect_uri` if sent, and `S256(code_verifier)` against the sealed challenge, before anything reaches the provider. The incoming `client_id` is the extension's and is ignored.
- **refresh-token** forwards a refresh grant, or answers 400 `unsupported_grant_type` for a provider without refresh tokens (GitHub, Webflow). **token** takes a refresh grant too, since `OAuthService` refreshes Google, Atlassian, Zoom and Notion at their token URL. A rotated refresh token (Atlassian's, Zoom's) comes back in the provider's answer, passed through unchanged. So does an answer without one (Figma's): `OAuthService` then keeps the refresh token it has.
- **The relay's own parameters can't be overridden.** `ownParams` keeps `client_id`, `redirect_uri`, `state`, `response_type`, `scope` and the PKCE parameters out of what passes through to the provider; the relay sets each itself (PKCE only where the provider uses it).
- **The exchange** asks for JSON (`Accept`), since GitHub answers form-encoded otherwise, and still reads a form-encoded answer (expiry times become numbers). It never follows a redirect. GitHub and Slack report errors with a 200 (`{"error": …}`, `{"ok": false}`), so `isProviderError` checks the body. A provider's refusal is a 400 with its `error`; a failure, an unreadable answer or a redirect is a 502 `temporarily_unavailable`. A success passes the provider's JSON through unchanged: `OAuthService.slack`'s default `tokenResponseParser` reads `authed_user.access_token`, and Linear's array `scope` is normalised by `OAuthService` itself.

## Rules

- **Never log secrets.** Request logs carry only the path (never the query), the provider, the status and the duration. Other log lines carry the provider and an upstream status. Never log a body, a query string, a header, an error that might quote one, or a config value other than the listen address, public URL and provider names. At start (`logStart` in `main`) it also logs one line per service with its callback URL, built from those alone. `checkLogs` in the tests greps the log for every secret, code, state, verifier and token a test saw; keep it in each new flow test.
- **Nothing is stored.** No database, no cache, no sessions. Anything a later step needs goes into a sealed value.
- Standard library first. The one dependency is `go.yaml.in/yaml/v3`. A new one must be pinned and AGPL-compatible, and clearly worth it.
- Error pages are `html/template`, so a provider name from the path is escaped. Token endpoints answer OAuth-style JSON errors (`error`, `error_description`), which `OAuthService` shows in its error message.
- Conventional commits (`feat: …`, `fix: …`, `test: …`, `ci: …`, `docs: …`).

## Tests

`make test` (`go test -race ./...`) and `make lint` (gofmt, `go vet`, and staticcheck and actionlint pinned in the Makefile). CI runs both on Ubuntu, then builds the image and reports its size, starts it and checks `/healthz`, the front page and `healthcheck`, checks that `healthcheck` fails without CA certificates (`SSL_CERT_FILE` and `SSL_CERT_DIR` pointed at nothing, so no network is needed), and runs it again with a generated certificate over HTTPS until the image's own health check reports healthy.

`internal/relay` tests run the relay against fake providers (`fake_test.go`): `httptest` servers that check each request the way that provider would (client credentials, body encoding, `Accept`, the relay's callback, PKCE) and answer with that provider's documented response shapes, including its error shapes. `relay_test.go` pins what Fudge and `OAuthService` send: the authorize parameters, and the token and refresh bodies field for field, as JSON and as `URLSearchParams`. No test reaches a real provider or the network. Time is a `WithClock` option, so expiry tests advance a fake clock. The harness's `t` is the top-level test's, used only by the fakes from their own goroutines; helpers take the running (sub)test's `t`.

## The image and releases

- **The image is `FROM scratch`:** the static binary and the build stage's CA bundle (the relay calls the services over HTTPS), as user `65532:65532`. Nothing else goes in without a reason. The build stage runs on `$BUILDPLATFORM` and cross-compiles with `TARGETOS`/`TARGETARCH`, so no emulation is needed. No time zone data: the relay only compares and logs times, in UTC.
- **`.github/workflows/release.yml`** runs on a pushed `v*` tag: the tag must be `v` + semver (no build metadata), then lint and tests, then the amd64 image is built and smoke-tested, then both platforms are pushed to `ghcr.io/jakeobsen/fudge-oauth` with `docker/metadata-action`'s tags (`{{version}}`, and `latest` only for a release, never a pre-release), labels and annotations (manifest and index). Only that job has `packages: write`; it logs in with the workflow's own `GITHUB_TOKEN`.
